Essential AI Knowledge

Topic 1.3

AI vs Machine Learning vs Deep Learning

  • AI is the umbrella: any system that mimics human cognitive tasks — reasoning, perception, decision-making.
  • Machine Learning (ML) is a subset of AI: systems that learn patterns from data rather than being explicitly programmed.
  • Deep Learning (DL) is a subset of ML: uses multi-layered neural networks. Powers computer vision, NLP, generative AI.
  • Every DL system is ML and AI; not every AI system is ML or DL.
Subset relationship
Topic 1.4

Why AI progress accelerated recently — four drivers

  • Data. Internet-scale corpora, sensors, labeled datasets — training material at previously impossible scale.
  • Compute. GPU parallelism (thousands of cores) makes training deep networks tractable.
  • Algorithms. Transformer architecture (2017) enabled attention-based models and modern LLMs.
  • Open-source frameworks. PyTorch, TensorFlow, CUDA, Hugging Face — researchers can share and reproduce.
Four levers behind the acceleration
Topic 1.8

GPU vs CPU architecture — the head-to-head

  • CPU optimizes for latency: a few complex cores with large caches, deep pipelines, branch prediction, out-of-order execution. Best for serial and diverse tasks.
  • GPU optimizes for throughput: thousands of simpler cores running in SIMT (Single Instruction, Multiple Threads) — the same op applied to massive data in parallel.
  • Matrix multiplication (the core of DL training and inference) is embarrassingly parallel — that's why GPUs dominate AI.
  • Modern systems pair them: CPU for orchestration, I/O, and serial logic; GPU for compute-heavy tensor work.
CPU: few complex cores · GPU: massive parallelism

Topic 1.1

NVIDIA software stack — from silicon to application

  • CUDA — parallel computing platform + programming model. The foundation everything else uses.
  • CUDA-X libraries — domain-specific: cuDNN (deep learning), cuBLAS (linear algebra), NCCL (multi-GPU comms), cuGraph, cuML.
  • RAPIDS — GPU-accelerated data science; pandas/scikit-learn API on GPU.
  • Frameworks — PyTorch, TensorFlow, JAX all sit on CUDA/cuDNN.
  • TensorRT — inference optimizer + runtime; compiles models to run fast on NVIDIA GPUs.
  • Triton Inference Server — production model server; handles multiple models, dynamic batching, multiple frameworks.
  • NeMo — framework for building/training/customizing generative AI (LLMs, speech, vision).
  • NVIDIA AI Enterprise — commercial suite with support; bundles the frameworks + tools for production.
  • NGC — the catalog: pre-trained models, containers, Helm charts, all optimized for NVIDIA hardware.
The stack — every layer above CUDA depends on it
Topic 1.7

AI development lifecycle — and which NVIDIA tool lives at each stage

  • Data ingestion & prep — ETL, cleaning, labeling. Tool: RAPIDS (GPU-accelerated pandas/dataframes).
  • Training — the compute-heavy step. Tools: PyTorch/TensorFlow on CUDA/cuDNN; NeMo for generative AI; NCCL for multi-GPU.
  • Validation — measure accuracy, bias, drift on held-out data.
  • Optimization — compile and quantize for target hardware. Tool: TensorRT.
  • Deployment — serve at scale. Tool: Triton Inference Server (multi-model, multi-framework, dynamic batching).
  • Monitoring — watch latency, throughput, accuracy drift, GPU health. Tool: DCGM for GPU metrics.
  • Retraining — loop back when data drifts or accuracy drops. This is what makes it a cycle, not a line.
Seven stages · one NVIDIA tool per stage

AI Operations

Topic 3.1

Data center management & monitoring essentials

  • NVIDIA Base Command — full-stack management for AI clusters: user access, dataset management, job scheduling, workload orchestration.
  • Baseboard Management Controller (BMC) — dedicated micro-controller on the server board; provides out-of-band control via IPMI/Redfish for power on/off, thermal readings, remote console, firmware updates.
  • Out-of-band management network — a physically separate network used only for BMC/lights-out control. Isolates admin traffic from data traffic; keeps you in when the primary network fails.
  • In-band vs out-of-band — know the difference. In-band shares the data network; out-of-band uses a dedicated management network.
Two networks, two purposes
Topic 3.2

Cluster orchestration & job scheduling — Slurm vs Kubernetes

  • Slurm — the HPC batch workload manager. Submit jobs to a queue, partition into nodes, gang-schedule for MPI/multi-node training. Traditional HPC choice.
  • Kubernetes (K8s) — container orchestration. Uses the NVIDIA GPU Operator to install drivers/toolkit/DCGM inside the cluster automatically.
  • Containers (Docker) package model + deps + framework versions — portable, reproducible runs.
  • Base Command Platform sits above these tools for end-to-end AI workflow orchestration.
  • Exam heuristic: HPC-style batch training → Slurm; production inference services / mixed workloads → Kubernetes.
Two orchestrators, two philosophies
Topic 3.3

GPU monitoring — DCGM and what to measure

  • NVIDIA DCGM (Data Center GPU Manager) is the standard tool. Exports metrics, runs diagnostics, integrates with Prometheus/Grafana.
  • Core metrics: GPU utilization %, memory used/free, temperature, power draw (watts), ECC errors, NVLink throughput, PCIe throughput.
  • Low GPU utilization is the classic complaint. Common causes: CPU-bottlenecked data loader, small batch size, I/O-bound pipeline, single-GPU code in a multi-GPU box, wrong precision, misconfigured MIG partitions.
  • DCGM ships with dcgmi CLI, a daemon, and Kubernetes/Prometheus exporters.
Four metrics DCGM always shows first
Topic 3.4

Virtualizing accelerated infrastructure — MIG · vGPU · Passthrough

  • MIG (Multi-Instance GPU) — hardware partitions one A100/H100 into up to 7 isolated GPU instances, each with dedicated compute + memory. Best for multi-tenant AI workloads that need real isolation.
  • vGPU — time-slices a GPU across multiple VMs. Common for graphics/VDI. Different mechanism from MIG (software slicing vs hardware partition).
  • Passthrough — assign a whole physical GPU to a single VM. Maximum performance, no sharing.
  • Exam trap: MIG is hardware isolation; vGPU is time-sliced. Different tools, different use cases.
Same GPU · three sharing models
